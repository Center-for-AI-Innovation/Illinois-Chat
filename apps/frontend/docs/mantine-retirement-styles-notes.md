# Mantine retirement — styles notes

Running log of the Tailwind/CSS written while replacing Mantine components, so we can spot repeated patterns and decide what to **elevate** to the global Tailwind config (`tailwind.config.ts`) or a shared `@layer components` in `globals.css`. All existing `--illinois-*` / `--navbar-*` / `--foreground*` CSS variables are reused verbatim, so colors match 1:1 across the migration.

## Elevation candidates (review before Phase 3)

| Pattern                                                                                                                                                        | Where it appears                                         | Suggested home                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Shine sweep on hover** (diagonal white gradient swept via `::after`, 650ms)                                                                                  | `AuthMenu` avatar                                        | `@layer components { .shine-on-hover { … } }` in globals.css, or a Tailwind plugin utility |
| **Illinois-orange outline button** (`h-9 min-w-[100px] border border-[--illinois-orange] text-[--illinois-orange] hover:bg-[rgb(255_95_5_/_0.05)]`)            | `AuthMenu` sign-in, `GlobalHeader` nav links + menu icon | shared `<Button variant="illinoisOutline">` or a `.btn-illinois-outline` component class   |
| **Navbar link** (`text-[13px] font-medium text-[--navbar-foreground] hover:text-[--navbar-hover] hover:bg-[--navbar-hover-background] data-[active=true]:...`) | `Navbar` desktop + mobile links                          | `.navbar-link` component class                                                             |
| **montserratHeading font** (`${montserrat_heading.variable} font-montserratHeading`)                                                                           | everywhere in chrome                                     | already a shared pattern; consider a `<Heading>`/`font-heading` utility                    |

## Per-component log

### Slice 1 — navbar chrome + static pages (2026-07-01)

> ⚠️ **Next 16 `next/font` weight gotcha (found via VR against production).** Under Next 16, `montserrat_heading` (700) and `montserrat_paragraph` (500) both resolve to family **`Montserrat`** with _both_ faces loaded — so `font-montserratHeading` no longer forces bold; the element's own `font-weight` now selects the face. Production (older Next) had a **700-only** `__Montserrat_*` heading family, so nav labels (whose CSS is `font-weight:500`, confirmed in the original `GlobalHeader` `link` createStyles) rendered at **700 anyway**. Net effect: any `font-montserratHeading` element with a non-700 weight renders **lighter** than production. Slice-1 nav buttons (`orangeOutlineBtn`, `navLinkClass`, AuthMenu sign-in) were `font-medium` → now **`font-bold`** so they render Montserrat 700 like production. **This is a Next-16 (wave-3c) side effect that affects heading text app-wide — audit heading weights against prod in every later slice.**

**UploadNotification.tsx** — `Card`(padding=0)→plain `<div>` (Paper-style bordered container, not the shadcn `Card` primitive, since padding/gap are fully custom via className and the default Card's `--card-spacing` would fight it). `Text`→`<p>`/`<pre>`. `Button variant="subtle" compact`→`<Button variant="ghost" size="icon-sm">`. Dead `Tooltip` import (unused) removed.

**ChatNavbar.tsx** — dropped `createStyles`/`useStyles` (its breakpoints varied by `isAdminOrOwner`, which CSS media queries can't express, so this was already computing effective visibility in JS via a tracked `windowWidth` state). Ported every `theme.fn.smallerThan/largerThan(isAdmin ? The `.link` class's narrow-viewport `list-item` compact variant was **dropped**: it only ever showed in a sliver of widths between two already-independent hide thresholds and wasn't visually load-bearing. **NavigationSidebar.tsx** — `createStyles`(theme-token slots, `&.collapsed`/`&:hover`/`&[data-active="true"]` combinators)→dropped entirely; every slot rewritten as a Tailwind class string, with `isOpen`/`isCollapsed` booleans branching into **mutually exclusive** class sets per property (e.g. `isCollapsed ? 'gap-0 p-3' : 'gap-3 px-4 py-3'`) rather than concatenating a base class with a same-property override — two same-specificity unprefixed Tailwind utility classes touching the same CSS property have no reliable "last one wins" guarantee from plain string concatenation (unlike component props run through `cn()`/`twMerge`, which resolves such conflicts explicitly). `&[data-active="true"]` (real usage here, unlike ChatNavbar) → Tailwind's `data-[active=true]:` variant. The dead `classes.navText` slot (defined but never referenced in JSX — the actual collapse-hide for nav labels happens via an inline `md:${isCollapsed ? 'hidden':'inline'}` at the call site) was dropped, not ported. `theme.radius.md/lg`→`rounded-(--radius-md)`/`rounded-(--radius-lg)`, `theme.shadows.sm/md`→Tailwind's built-in `shadow-sm`/`shadow-md` (no matching CSS var exists; fidelity bar applied).

**Sidebar.tsx** — only `Button` and `Tooltip` remained (rest of the file was already shadcn/Tailwind). `Tooltip`(`label`, `disabled`, `withArrow`, `position="right"`, `withinPortal`)→`Tooltip disabled={…}` + `TooltipTrigger render={<div .../>}` (Base UI's `disabled` prop is native on `Tooltip.Root`, so the Mantine `disabled` prop ports 1:1) + `TooltipContent side="right"` (arrow renders by default, matching `withArrow`; Base UI always portals, matching `withinPortal`).
