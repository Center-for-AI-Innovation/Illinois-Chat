# Configuration reference

Every variable the stack reads, grouped by service, with where it is read and whether it has a default. Authentication and model setup are covered in prose at the end.

## Environment files

There are two environment modes:

- **Full Docker stack** (`infra/scripts/start-all.sh`) — reads the repository-root `.env`, created from `.env.template` on the first run. Compose maps values into each container and uses Docker service names for internal URLs. Crawlee and the dev Keycloak container load the whole `.env` via `env_file`; every other container receives exactly the variables listed in its `environment:` block.
- **Local development** (`infra/scripts/start-dev.sh`) — Docker runs only the infrastructure; the app processes read their own files, `apps/backend/.env`, `apps/frontend/.env` and `apps/crawlee/.env`, which the script creates and appends missing keys to without overwriting existing values.

Four template files exist. The **In template** column below says which one carries the variable:

| Value | File | Who reads it |
| --- | --- | --- |
| root | `.env.template` | copied to `.env` by `start-all.sh`; also sourced by `start-dev.sh` |
| worker | `apps/backend/ai_ta_backend/rabbitmq/.env.template` | the ingest worker when run on its own (`python worker.py`) |
| none | — | read from the process environment only |

`apps/backend/.env.template` and `apps/frontend/.env.template` are dev reference files: no script reads them (`start-dev.sh` writes the app `.env` files itself), so a variable that appears only there has no effect on either stack.

!!! danger "Never commit `.env` files"
    Environment files contain secrets. They are gitignored — keep it that way.

**Read by** uses three columns: *full* (`docker-compose.yaml`), *dev* (`docker-compose.dev.yaml` and the app `.env` files `start-dev.sh` writes) and *sim* (`docker-compose.sim.yaml`). *Required* means Compose refuses to start without it (`:?`).

| `QDRANT_API_KEY` | full, dev | no default; must match `api_key` in `qdrant_config.yaml` | root |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | full, dev | no default (template: `minioadmin`) | root |

`ENCRYPTION_MASTER_KEY` encrypts each chatbot's stored Sim API key and the external-connection configs. Changing it later means every chatbot's Sim key has to be re-entered.

## Authentication (Keycloak)

| Variable | Read by | Required or default | In template |
| --- | --- | --- | --- |
| `KEYCLOAK_ADMIN_USERNAME` | full, dev, sim | `admin` | root |
| `NEXT_PUBLIC_KEYCLOAK_URL` | dev | `http://localhost:8080/` (full stack: hardcoded build arg) | root |
| `NEXT_PUBLIC_KEYCLOAK_REALM` | dev, sim | `illinois_chat_realm` (full stack: hardcoded build arg) | root |
| `NEXT_PUBLIC_KEYCLOAK_CLIENT_ID` | dev | `illinois_chat` (full stack: hardcoded build arg) | root |
| `NEXT_PUBLIC_USE_ILLINOIS_CHAT_CONFIG` | dev | `True` (full stack: hardcoded build arg) | root |
| `NEXT_PUBLIC_SIGNING_KEY` | dev | empty | root |
| `SUPER_ADMIN_EMAILS` | full, dev | empty; comma-separated | root |
| `NEXT_PUBLIC_SUPER_ADMIN_EMAILS` | dev | empty; set to the same value as `SUPER_ADMIN_EMAILS` | root |
| `DEFAULT_COURSE_ADMINS` | full, dev | empty; comma-separated admins added to every new chatbot (backend) | root |

`NEXT_PUBLIC_SIGNING_KEY` encrypts the provider API keys chatbots store on their LLMs page. Without it those keys are stored in plaintext.

Illinois Chat uses [Keycloak](https://www.keycloak.org/) for authentication. The Docker stack bootstraps a ready-to-use realm from `infra/keycloak/realms/`:

- **Realm:** `illinois_chat_realm`
- **Client ID:** `illinois_chat`
- **Admin console:** `http://localhost:8080` (log in with `KEYCLOAK_ADMIN_USERNAME` / `KEYCLOAK_ADMIN_PASSWORD`)

The frontend authenticates users via OIDC against this realm. User records live in Postgres. Typical customizations in the Keycloak admin console:

- **Identity providers** — federate with an institution's SSO (SAML/OIDC) so users log in with existing accounts.
- **User federation** — connect LDAP/Active Directory.
- **Theme** — the Illinois Chat login theme ships in `infra/keycloak/theme/`.

!!! warning "Change the admin password"
    The default Keycloak admin password is `admin`. Change it before exposing the stack anywhere.

## Models and embeddings

| Variable | Read by | Required or default | In template |
| --- | --- | --- | --- |
| `EMBEDDING_MODEL` | full, dev | `Qwen/Qwen3-Embedding-8B` | root, worker |
| `EMBEDDING_API_BASE` | full, dev | frontend/worker: `http://host.docker.internal:11434/v1`; backend: no default | root, worker |
| `ALLOWED_EMBEDDING_PROVIDERS` | full, dev | `openai,ollama`; providers an external connection may use | worker |
| `NCSA_HOSTED_API_KEY` | full, dev | empty | root, worker |
| `NCSA_HOSTED_VLM_BASE_URL` | full, dev | empty; enables the hosted default tier of [tool routing](../how-it-works/tool-routing.md) | root |
| `TOOL_ROUTER_MODEL_ID` | dev | empty; model used for tool routing on the hosted endpoint. Not passed by Compose, so the full stack always uses the hosted default model | root |
| `OLLAMA_SERVER_URL` | full, dev | empty | root, worker |
| `VLADS_OPENAI_KEY`, `OPENAI_API_KEY` | dev | empty; not passed by Compose | root (`VLADS_OPENAI_KEY` only) |

Chat models are configured per chatbot on its [LLMs page](../building/llms.md), not server-side. On a self-hosted stack the common setups are:

- **Bring-your-own-key** — chatbot owners paste OpenAI, Anthropic or Azure keys on the LLMs page; nothing to configure server-side.
- **Local serving** — run Ollama or vLLM (optionally via `infra/docker/docker-compose.models.yaml`) and set `OLLAMA_SERVER_URL`, or point an OpenAI-compatible provider at the endpoint.
- **NCSA-hosted** — set `NCSA_HOSTED_API_KEY` and `NCSA_HOSTED_VLM_BASE_URL` if you have access.

Retrieval depends on a single embedding model configured deployment-wide. The default is **Qwen3-Embedding-8B** (4096-dimensional vectors) served from any OpenAI-compatible endpoint (Ollama, vLLM, a hosted API):

```env
EMBEDDING_MODEL=Qwen/Qwen3-Embedding-8B
EMBEDDING_API_BASE=http://host.docker.internal:11434/v1
```

If you switch to a model with a different dimension, set `QDRANT_VECTOR_SIZE` to match before the first start; the start scripts recreate a Qdrant collection whose size does not match.

## Vector database (Qdrant, optional)

The default vector store is pgvector in the application Postgres. Qdrant is started by both stacks and used only by chatbots whose [external connection](external-connections.md) names a `qdrant` config. Qdrant reads `qdrant_config.yaml` at the repository root; its `api_key` must match `QDRANT_API_KEY` in `.env`. The start scripts create the collection named in `QDRANT_COLLECTION_NAME` with `QDRANT_VECTOR_SIZE` cosine vectors.

## Database schema

- The schema is applied from `infra/db/init-schema.sql` only when a start script runs with `--create-schema` (empty database) or `--wipe_data` / `--clean` (reset). A plain start on an empty database stops with "Database is empty".
- Drizzle migrations `0016` and `0017` are replayed by both start scripts on every boot (`0016` adds the Sim columns, `0017` encrypts `projects.sim_api_key`); both are no-ops once applied.
- Every other migration under `apps/frontend/src/db/migrations` is applied with `npm run db:migrate` from `apps/frontend`. Migrations touch only the host database; see [External connections](external-connections.md) for external stores.

## What the images contain

The frontend, backend and worker images are built with `COPY . .` and no `.dockerignore`, and the backend and worker call `load_dotenv()` on start:

- **Frontend** (context `apps/frontend`): the runner stage copies no `.env`, so server-only variables not listed in Compose's frontend `environment:` block (for example `TOOL_ROUTER_MODEL_ID`) are unset in the container. `NEXT_PUBLIC_*` values are inlined by `next build`, so values not passed as build args (`NEXT_PUBLIC_SIGNING_KEY`, `NEXT_PUBLIC_SUPER_ADMIN_EMAILS`) are present only if an `apps/frontend/.env` existed on the build machine.
- **Backend** (context `apps/backend`): an `apps/backend/.env` left behind by an earlier `start-dev.sh` run is baked into the image and read at runtime, secrets included.
- **Worker** (context `apps/backend/ai_ta_backend/rabbitmq`): bakes only a `.env` created from the worker template in that directory.

Statements on this site such as "`/canvas_ingest` returns 500" or "no export email is sent" describe a clean build; a baked `.env` changes them.

Root-template variables that no Compose file passes on and that therefore have no effect on the full stack: `NEXT_PUBLIC_KEYCLOAK_URL`, `NEXT_PUBLIC_KEYCLOAK_CLIENT_ID`, `NEXT_PUBLIC_USE_ILLINOIS_CHAT_CONFIG` (hardcoded build args), `NEXT_PUBLIC_SIGNING_KEY`, `NEXT_PUBLIC_SUPER_ADMIN_EMAILS`, `TOOL_ROUTER_MODEL_ID`, `VLADS_OPENAI_KEY`, `NEXT_PUBLIC_POSTHOG_*`, `NOMIC_API_KEY`, `SENTRY_DSN`, `MINIO_*`, `SIM_ALLOWED_SIM_ORIGINS`.
